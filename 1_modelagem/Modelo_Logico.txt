MODELO LÓGICO — CLÍNICA RARE

1. Visão geral

O modelo lógico representa a estrutura relacional do banco de dados da Clínica Rare. As tabelas abaixo foram definidas a partir do modelo conceitual e do script SQL do projeto.

2. Tabelas, atributos, chaves e restrições

2.1 CONVENIO
- id_convenio INT NOT NULL — PK
- nome_convenio VARCHAR(150) NOT NULL
- cnpj VARCHAR(18) — UNIQUE
- telefone VARCHAR(15)
- email VARCHAR(100)
- cobertura VARCHAR(200)
- tipo_plano VARCHAR(50)
- endereco VARCHAR(200)

2.2 PACIENTE
- id_paciente INT NOT NULL — PK
- CPF VARCHAR(14) NOT NULL — UNIQUE
- nome VARCHAR(100) NOT NULL
- endereco VARCHAR(150) NOT NULL
- genero VARCHAR(50) NOT NULL
- email VARCHAR(100) NOT NULL
- telefone VARCHAR(15) NOT NULL
- data_nascimento DATE NOT NULL
- id_convenio INT — FK para CONVENIO(id_convenio)

2.3 MEDICO
- id_medico INT NOT NULL — PK
- CRM VARCHAR(20) NOT NULL — UNIQUE
- especialidade VARCHAR(70) NOT NULL
- nome VARCHAR(100) NOT NULL
- telefone VARCHAR(15) NOT NULL
- data_contratacao DATE NOT NULL
- endereco VARCHAR(100) NOT NULL
- email VARCHAR(100) NOT NULL

2.4 REGISTROS_CONSULTAS
- id_consulta INT NOT NULL — PK
- data_consulta DATE NOT NULL
- horario TIME NOT NULL
- motivo VARCHAR(200)
- diagnostico VARCHAR(300)
- observacoes TEXT
- id_paciente INT NOT NULL — FK para PACIENTE(id_paciente)
- id_medico INT NOT NULL — FK para MEDICO(id_medico)

2.5 PRONTUARIOS_ELETRONICOS
- id_prontuario INT NOT NULL — PK
- data_criacao DATE NOT NULL
- historico_medico TEXT
- alergias TEXT
- medicamentos TEXT
- observacoes TEXT
- tipo_sanguineo VARCHAR(5)
- id_paciente INT NOT NULL — FK para PACIENTE(id_paciente)

2.6 FUNCIONARIOS
- id_funcionario INT NOT NULL — PK
- nome VARCHAR(150) NOT NULL
- cpf VARCHAR(14) NOT NULL — UNIQUE
- cargo VARCHAR(80)
- data_admissao DATE
- telefone VARCHAR(15)
- email VARCHAR(100)
- salario DECIMAL(10,2)

2.7 PAGAMENTOS
- id_pagamento INT NOT NULL — PK
- data_pagamento DATE NOT NULL
- horario_pagamento TIME
- forma_pagamento VARCHAR(30)
- valor DECIMAL(10,2) NOT NULL
- situacao VARCHAR(30)
- descricao VARCHAR(200)
- id_paciente INT NOT NULL — FK para PACIENTE(id_paciente)
- id_funcionario INT NOT NULL — FK para FUNCIONARIOS(id_funcionario)
- data_vencimento DATE NOT NULL

3. Relacionamentos

3.1 CONVENIO → PACIENTE
- Chave estrangeira: PACIENTE.id_convenio
- Referência: CONVENIO.id_convenio
- Um convênio pode estar associado a vários pacientes.
- Um paciente pode possuir um convênio; o campo id_convenio é opcional no banco.

3.2 PACIENTE → REGISTROS_CONSULTAS
- Chave estrangeira: REGISTROS_CONSULTAS.id_paciente
- Referência: PACIENTE.id_paciente
- Um paciente pode possuir vários registros de consultas.
- Cada registro de consulta pertence a um único paciente.

3.3 MEDICO → REGISTROS_CONSULTAS
- Chave estrangeira: REGISTROS_CONSULTAS.id_medico
- Referência: MEDICO.id_medico
- Um médico pode realizar vários registros de consultas.
- Cada registro de consulta pertence a um único médico.

3.4 PACIENTE → PRONTUARIOS_ELETRONICOS
- Chave estrangeira: PRONTUARIOS_ELETRONICOS.id_paciente
- Referência: PACIENTE.id_paciente
- O banco permite que um paciente tenha registros de prontuário associados.
- Cada registro de prontuário pertence a um único paciente.
- Observação: não existe restrição UNIQUE em id_paciente nessa tabela, portanto o modelo físico implementado permite mais de um prontuário por paciente.

3.5 PACIENTE → PAGAMENTOS
- Chave estrangeira: PAGAMENTOS.id_paciente
- Referência: PACIENTE.id_paciente
- Um paciente pode possuir vários pagamentos.
- Cada pagamento pertence a um único paciente.

3.6 FUNCIONARIOS → PAGAMENTOS
- Chave estrangeira: PAGAMENTOS.id_funcionario
- Referência: FUNCIONARIOS.id_funcionario
- Um funcionário pode registrar vários pagamentos.
- Cada pagamento é registrado por um único funcionário.

4. Resumo das chaves estrangeiras

- PACIENTE.id_convenio → CONVENIO.id_convenio
- REGISTROS_CONSULTAS.id_paciente → PACIENTE.id_paciente
- REGISTROS_CONSULTAS.id_medico → MEDICO.id_medico
- PRONTUARIOS_ELETRONICOS.id_paciente → PACIENTE.id_paciente
- PAGAMENTOS.id_paciente → PACIENTE.id_paciente
- PAGAMENTOS.id_funcionario → FUNCIONARIOS.id_funcionario

5. Integridade

As chaves primárias identificam unicamente os registros de cada tabela. As chaves estrangeiras mantêm os vínculos entre as entidades. As restrições UNIQUE evitam duplicidade de CPF dos pacientes e funcionários, de CRM dos médicos e de CNPJ dos convênios, conforme definido no script SQL.

6. Observação

Este documento descreve o modelo lógico conforme implementado no script SQL da Clínica Rare, mantendo os nomes das tabelas e dos atributos utilizados no projeto.
